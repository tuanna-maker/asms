§01 Nguyên tắc

1. Nguyên tắc triển khai on-premise

ASMS được triển khai hoàn toàn trong hạ tầng nội bộ của đơn vị: không phụ thuộc cloud, không có traffic ra ngoài Internet trong luồng xử lý. Chỉ cổng 80/443 được mở ra ngoài qua reverse proxy; backend và database chỉ giao tiếp qua mạng nội bộ (docker network hoặc VLAN riêng).

1.1 Các nguyên tắc cốt lõi

  • Dữ liệu nằm tại chỗ: PostgreSQL + uploads volume lưu trên server/VM nội bộ, không đồng bộ cloud.
  • Tối thiểu surface ngoài: chỉ Nginx reverse proxy được public; backend, DB, backup ở mạng riêng.
  • Tách biệt trách nhiệm: mỗi container đảm nhận một trách nhiệm duy nhất (frontend / backend / db).
  • Cấu hình qua biến môi trường: .env là nguồn cấu hình duy nhất, không hard-code trong image.
  • Backup có chủ đích: cron backup hằng ngày cho cả DB lẫn uploads, retention 30 ngày.
  • Defense in depth: nhiều lớp kiểm soát (edge, transport, gateway, app, auth, data).

1.2 Stack công nghệ

Frontend: React + Vite + TailwindCSS + shadcn/ui Backend: Node.js 20 + Express + TypeScript ORM: Prisma 6 DB: PostgreSQL 16 Auth: JWT (access 1h + refresh 30d) Reverse proxy: Nginx 1.27-alpine Container runtime: Docker Engine / Docker Compose
Lưu ý: JWT secret phải có độ dài tối thiểu 32 ký tự. Backend sẽ từ chối boot nếu JWT_SECRET quá yếu hoặc chưa được thiết lập ở môi trường production (xem backend/src/config/validateEnv.ts).

§04 Data flow

4. Luồng dữ liệu điển hình

Trình duyệt người dùng truy cập hệ thống qua HTTPS; backend xử lý và đọc/ghi database trong mạng nội bộ. File đính kèm được lưu vào volume backend/uploads và phát lại qua API có bảo vệ JWT.

BướcTừĐếnHành động
1Trình duyệt người dùngNginx (443)GET / — mở trang chủ
2Nginxasms_frontend (80)Serve SPA + index.html fallback
3Trình duyệtNginx (443)POST /api/v1/auth/login
4Nginxasms_backend (4001)proxy_pass /api/
5BackendPostgreSQL (5432)Prisma + JWT verify, audit log
6BackendUploads volumeMulter lưu file đính kèm
7Cron (02:00)Backup serverpg_dump + tar mỗi ngày

4.1 Hai luồng chính cần hiểu

Luồng đọc (read): Browser → Nginx (443) → proxy /api/ → Backend (4001) → Prisma → PostgreSQL (5432) → trả ngược lại theo chuỗi.
Luồng ghi (write): Browser gửi form → Nginx → Backend xác thực JWT + RBAC → ghi DB + ghi audit_logs → lưu file (nếu có) vào uploads volume.
Đặc điểm: tất cả response đều đi theo chuẩn JSON { success, data, message? }, prefix /api/v1. Mọi input đều validate bằng Zod (xem backend/src/modules/*/route.ts). File đính kèm được truy cập qua /api/v1/uploads/* và bắt buộc có JWT hợp lệ — không lộ file công khai.

§05 Port map

5. Bản đồ cổng (Port map)

Tổng hợp các cổng được sử dụng trong triển khai on-premise. Cổng 5432 (PostgreSQL) và cổng backend 4001 chỉ nên bind trong mạng nội bộ — không publish ra host.

SurfacePortĐi đếnGhi chú
HTTPS443NginxTLS terminate
HTTP → HTTPS80Nginx301 redirect về HTTPS
Frontend public (docker-compose expose)8080asms_frontendCó thể đổi sang 80 nếu dùng host network
Backend (internal)4001asms_backendChỉ trong docker network nội bộ
PostgreSQL5432postgresChỉ từ backend host, không public
Healthcheck4001/api/v1/healthPing DB SELECT 1

5.1 Cấu hình docker-compose tham chiếu

Trong docker-compose.yml, chỉ Nginx (qua nginx.prod.conf) mới được publish 80:80 và 443:443 ra host. Container backend và DB chỉ nội bộ (không có ports: mapping ra host) hoặc map sang cổng khác cho debug.

Ví dụ: docker-compose port mapping (rút gọn)
services:
  nginx:
    ports:
      - "80:80"
      - "443:443"
  asms-backend:
    expose:
      - "4001" # không publish ra host
  asms-db:
    expose:
      - "5432" # chỉ trong docker network
Khuyến nghị: tuyệt đối không publish cổng 5432 ra host Internet. Nếu cần debug DB từ máy khác, dùng SSH tunnel hoặc VPN vào bastion.

6. Thông số phần cứng tối thiểu

Mức đề xuất cho khoảng 50–150 user đồng thời, lượng dữ liệu vài trăm GB. Tăng CPU/RAM theo số user đồng thời và dung lượng upload tài liệu đính kèm.

6.1 Ghi chú chọn phần cứng

  • CPU: DB là tầng nhạy cảm nhất — ưu tiên CPU có clock cao cho query, không nhất thiết nhiều core.
  • RAM: PostgreSQL nên có shared_buffers ≈ 25% RAM; backend dành RAM cho Multer upload file lớn.
  • Disk: dùng SSD cho DB host; backup host có thể dùng HDD dung lượng lớn.
  • Mạng: card mạng 1 Gbps tối thiểu trong VLAN; 10 Gbps nếu tải lớn hoặc streaming replication.
Quy tắc sizing: mỗi 50 user đồng thời tăng thêm ~1 vCPU + ~2 GB RAM cho backend, và ~4 GB RAM cho DB. Disk DB tăng ~100 GB mỗi năm tuỳ lượng audit log + attachment.

9.1 Quy trình restore khi sự cố

  1. Liệt kê các bản backup gần nhất: ls -lh /opt/asms/backups/
  2. Chọn bản asms_db_YYYYMMDD.sql.gz + asms_uploads_YYYYMMDD.tar.gz mới nhất còn nguyên vẹn.
  3. Dừng containers: docker compose down
  4. Khôi phục DB: gunzip -c asms_db_*.sql.gz | docker exec -i asms-db psql -U asms
  5. Khôi phục uploads: tar -xzf asms_uploads_*.tar.gz -C backend/uploads
  6. Redeploy image trước đó (nếu rollback code): docker compose up -d
  7. Verify health: curl /api/v1/health và đăng nhập thử bằng 1 tài khoản.
  8. Ghi incident + thông báo VTX theo quy trình.
Lưu ý: nếu sự cố xảy ra trong vòng 24h sau backup gần nhất, dữ liệu phát sinh sau thời điểm đó sẽ mất. Có thể giảm RPO bằng cách tăng tần suất backup hoặc bật PostgreSQL streaming replication sang máy dự phòng.

10.1 Healthcheck endpoint

Endpoint GET /api/v1/health trả về trạng thái tổng quan của service kèm khả năng kết nối DB:

Curl mẫu
curl -s https://asms.vtx.local/api/v1/health | jq .
# Response mẫu:
# { "success": true, "data": { "status": "ok", "database": "reachable", "uptime": 3600 } }

10.2 Metric đề xuất thu thập

  • App: request rate, p95/p99 latency, error rate 4xx/5xx, JWT verify fail.
  • DB: connection count, replication lag (nếu bật), slow query, locks.
  • Infra: CPU, RAM, disk I/O, network in/out theo host.
  • Business: số ticket bảo hành mở, số hợp đồng sắp hết hạn (query bảng contracts).
Khuyến nghị: với hệ thống quy mô vài chục user, có thể dùng Uptime Kuma (self-hosted, miễn phí) để probe /api/v1/health và gửi cảnh báo qua Telegram/email khi down. Logs tổng hợp bằng Dozzle hoặc docker logs + logrotate.
